Clase 11–12 · Telegram como canal del chatbot

En la clase anterior construimos una conversación con historial y una interfaz conectada con FastAPI. Hoy llevaremos esas mismas funciones a Telegram para que una persona consulte el negocio desde su teléfono o computador.

Vamos a crear el bot, recibir sus mensajes y distinguir los comandos de las preguntas. Al terminar, cada equipo deberá demostrar una consulta real desde Telegram hasta los datos de su proyecto.

Qué cambia cuando usamos Telegram

Telegram entrega el mensaje a nuestro programa. El archivo bot_telegram.py extrae el texto, llama la función de conversación y envía el resultado al chat. Ese archivo adapta el canal a la lógica que ya tenemos.

1. TelegramLa persona escribe y el bot recoge el evento.
2. AdaptadorUn manejador recibe el texto y llama al proyecto.
3. ProyectoEl modelo interpreta y FastAPI consulta el negocio.
4. RespuestaEl adaptador convierte el resultado en un mensaje.

El cliente de FastAPI y las funciones de conversación siguen en sus módulos. El nuevo archivo se ocupa de la entrada y la salida de Telegram.

La cuenta del bot y el programa que responde

Crear un bot registra una identidad en Telegram: un nombre visible y un nombre de usuario que podremos compartir. Para que esa cuenta responda con nuestro proyecto, hace falta un proceso Python que esté funcionando con su token.

ParteQué aporta
Cuenta de TelegramPermite encontrar el bot y abrir su conversación.
Proceso PythonRecoge los eventos, ejecuta los manejadores y prepara las respuestas.
Servicios del proyectoEl modelo interpreta las consultas y FastAPI accede al negocio.

Si detenemos Python, la cuenta sigue apareciendo. Las funciones del proyecto dejan de atender mientras el proceso esté apagado.

El token que entrega BotFather permite que Python utilice la Bot API en nombre de esa cuenta. Es diferente de la clave de Groq: cada credencial autoriza el acceso a un servicio distinto.

Cómo llegan los mensajes: long polling

El programa inicia una solicitud a Telegram y espera nuevas actualizaciones. Cuando llegan, la biblioteca las entrega a los manejadores registrados y continúa esperando. Ese ciclo se llama long polling.

La conexión comienza desde nuestro computador. Por eso podemos probar el bot sin publicar una dirección web para recibir eventos. Si FastAPI está en ese mismo equipo, el programa puede seguir consultándola en 127.0.0.1.

aplicacion.run_polling(allowed_updates=["message"])

Para un token ejecutamos una instancia de polling. Telegram también admite webhooks, donde envía los eventos a una dirección configurada. Hoy utilizaremos polling.

Fuentes: https://core.telegram.org/bots/api#getting-updates y https://core.telegram.org/bots/faq#how-do-i-get-updates

Update representa el evento recibido

Telegram entrega una actualización con los datos del evento. La biblioteca la convierte en un objeto Update. Primero comprobamos si existe un mensaje y luego extraemos su texto.

mensaje = update.effective_message
pregunta = mensaje.text
chat_id = update.effective_chat.id
persona_id = update.effective_user.id

El identificador del chat indica la conversación. El identificador de usuario indica quién intervino. En un grupo varias personas comparten el mismo chat.

Actualización recibida (fragmento)

{ "update_id": 55, "message": { "text": "¿Qué servicios ofrecen?", "chat": {"id": 3769874578, "type": "private"}, "from": {"id": 3769874578, "first_name": "Laura"} } }

El mensaje contiene el texto, el identificador del chat y los datos de quien lo envió.

Un handler asocia un evento con una función

Al registrar un manejador indicamos qué debe reconocer y qué función debe ejecutar. Para un comando utilizamos CommandHandler. El nombre del comando se escribe sin la barra dentro del registro.

aplicacion.add_handler(
    CommandHandler("help", ayuda)
)

Cuando llega /help, la biblioteca llama a ayuda(update, context). El manejador dirige el evento. La función define la respuesta.

Entrada: /help

Función seleccionada: ayuda() /start: mostrar la bienvenida. /help: ver esta ayuda. /reset: reiniciar esta conversación. Prueba: ¿Qué servicios ofrecen? O pregunta por disponibilidad indicando servicio y fecha. En esta versión las operaciones de reserva quedan sin ejecutar.

CommandHandler reconoce /help y entrega el evento a ayuda().

Los filtros seleccionan las preguntas del negocio

Este filtro admite texto de conversaciones privadas y excluye comandos. & exige ambas condiciones y ~ excluye la que sigue. Así una pregunta llega al chatbot y /help sigue su propia ruta.

privado = filters.ChatType.PRIVATE
filtro = privado & filters.TEXT & ~filters.COMMAND

aplicacion.add_handler(
    MessageHandler(filtro, recibir_texto)
)

El archivo también orienta ante fotos y comandos desconocidos. Los mensajes de grupo quedan fuera de esta primera implementación.

Resultados de las cuatro entradas

TEXTO PRIVADO recibir_texto(): muestra el catálogo. FOTO otro_mensaje(): Por ahora recibo consultas escritas. Envíame un mensaje de texto. COMANDO /precio comando_desconocido(): No conozco ese comando. Usa /start, /help o /reset. MENSAJE DE GRUPO Sin respuesta: el evento queda fuera del filtro.

Cada entrada sigue la función que corresponde a su filtro.

Fuente: https://docs.python-telegram-bot.org/en/stable/telegram.ext.filters.html

Por qué los manejadores usan async y await

async def define una función que puede participar en el procesamiento asíncrono. await espera una operación compatible con ese mecanismo. Cuando enviamos una respuesta, esperamos que termine la llamada de envío.

async def iniciar(update, context):
    mensaje = update.effective_message
    if mensaje is not None:
        await mensaje.reply_text("Hola. ¿Qué deseas consultar?")

Mientras una operación asíncrona espera la red, el bucle de eventos puede atender otras tareas preparadas. Escribir async no transforma automáticamente en asíncronas las funciones comunes que llamamos dentro.

Conservaremos el procesamiento secuencial de actualizaciones que utiliza la aplicación por defecto. La adaptación del cliente síncrono la veremos al conectar el módulo anterior.

Fuente: https://docs.python.org/3/reference/compound_stmts.html#coroutine-function-definition

/help explica lo que el bot admite

La ayuda ofrece los comandos y ejemplos válidos del negocio. Su respuesta se prepara directamente en Python. Mostrar la ayuda no necesita una consulta al modelo ni a FastAPI.

async def ayuda(update, context):
    await enviar_texto(
        update.effective_message, AYUDA
    )

La ayuda se prepara directamente en Python. No necesita consultar el modelo ni FastAPI.

La respuesta se envía con reply_text()

En la interfaz anterior, una función devolvía valores que Gradio mostraba en pantalla. En este canal debemos realizar el envío. Un return por sí solo termina la función sin presentar una respuesta en el chat.

texto = formatear_resultado(resultado, plan)
await mensaje.reply_text(texto)

Primero convertimos el resultado del proyecto en texto legible. Después esperamos la llamada que lo envía al mensaje recibido. El archivo entregado agrupa ese envío en la función enviar_texto().

La presentación puede adaptarse a cada negocio. Un catálogo debe mostrar datos útiles para la persona, como el servicio, el precio y la duración.

Conectamos el texto con procesar_turno()

El adaptador importa la función de la clase anterior. Le entrega la pregunta y el historial de ese chat. Recibe el resultado, los mensajes actualizados y el plan identificado.

from chatbot_memoria import nuevo_historial, procesar_turno

resultado, actualizado, plan = await asyncio.to_thread(
    procesar_turno, pregunta, historial, clave, modelo
)
context.chat_data["historial"] = actualizado
await enviar_texto(mensaje, formatear_resultado(resultado, plan))

El módulo anterior utiliza peticiones síncronas. asyncio.to_thread() las ejecuta en un hilo de trabajo y permite esperar el resultado desde el manejador. Pasamos la función sin paréntesis y después sus argumentos.

El archivo completo también comprueba la configuración y atiende errores antes de actualizar el historial.

Fuente: https://docs.python.org/3/library/asyncio-task.html#asyncio.to_thread

# Dentro del módulo que ya teníamos:
resultado = ejecutar(plan)

# De regreso en el adaptador:
texto = formatear_resultado(resultado, plan)
await enviar_texto(mensaje, texto)

Un fallo de conexión debe producir una orientación

El procesamiento puede fallar al consultar el modelo o FastAPI. El manejador debe avisar qué ocurrió y conservar el historial anterior. La actualización se hace después de obtener y preparar un resultado válido.

try:
    resultado, actualizado, plan = await asyncio.to_thread(...)
except (URLError, TimeoutError):
    await enviar_texto(mensaje, "No pude completar la conexión.")
    return

context.chat_data["historial"] = actualizado

Las respuestas extensas se dividen antes de enviarlas

Telegram admite hasta 4096 caracteres en un mensaje de texto. Un catálogo largo puede superar ese límite. El archivo entregado utiliza bloques de hasta 4000 caracteres y los envía en orden.

async def enviar_texto(mensaje, texto):
    for inicio in range(0, len(texto), 4000):
        await mensaje.reply_text(texto[inicio:inicio + 4000])

El corte de la cadena permite cumplir el límite. Para la presentación final del proyecto conviene agrupar por servicios o por párrafos, de modo que cada mensaje conserve una idea completa.

Trabajaremos con texto sencillo. El formato del mensaje debe permitir entender el resultado que devolvió el negocio.

registrar_handlers(aplicacion)

Conecten el bot de su negocio con las funciones del proyecto. La persona debe poder iniciar la conversación, consultar datos reales y completar una consulta en otro mensaje.

  1. Registren el bot y adapten la bienvenida y la ayuda.
  2. Añadan el archivo entregado, instalen la dependencia y revisen los imports.
  3. Inicien FastAPI y el proceso de Telegram con la configuración del equipo.
  4. Prueben comandos, catálogo y disponibilidad. Comparen los resultados con la API.
  5. Comprueben reinicio, comando desconocido y una consulta con la API detenida.

Cada integrante debe localizar el handler de entrada y explicar la llamada al módulo anterior. El resultado de hoy es una consulta real desde Telegram hasta los datos del negocio.

Qué debe quedar al terminar

Actualicen el repositorio con bot_telegram.py, sus dependencias y las instrucciones para ejecutarlo. Incluyan el enlace público del bot y expliquen qué proceso debe permanecer encendido durante la demostración.

En la bitácora registren el recorrido de una consulta: evento recibido, handler seleccionado, función reutilizada y respuesta enviada. Añadan un problema de integración y cómo lo resolvieron o qué falta por resolver.

Las evidencias deben mostrar los comandos funcionando, una consulta real contrastada con FastAPI y una consulta que continúa en otro turno. En la explicación deben poder identificar qué añadió el canal y qué parte del proyecto se reutilizó.
